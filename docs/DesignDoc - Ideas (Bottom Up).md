
Basic Idea: agent should be able to control its context. Self context engineering. And we limit the space.

# Context Engineering

The active context at the start of any given round contains: system prompt + "registers" + tools (+ last part of history). 

"registers" is a structured data (let's make it a jsonified list) which contains N items (default N=32). There are N0 registers that are protected (cannot be written by agent).
Each item can only be None, int, bool, float, or str (None when initialized), and the length of the item (converted to str) cannot exceed L chars (default L=256). 

"registers" can be modified by a tool.

last part of history: If it is not the first model response, contain the last two parts: the last model response and the last tool use result / user response.   
  The two parts added together should not exceed L2 chars (default L2=1024), else truncate the two parts: if there is a part that is shorter than L20 chars (default L20=256), truncate the other part and only keep the head;    
  if both parts are longer than L20, truncate the shorter part to L20 and the other part to L2-L20, both keeping the head.

We can also indicate a zone for "strategy", where models can design their own strategy. This part will keep unchanged until the model sets a new one. In my opinion, though, this makes things more complicated and is not "elegant" enough, so ignore this in the beginning. However, we should keep in mind that we need something for the model to "bootstrap", i.e. it should be able to generate a strategy from scratch, and then stick to that strategy. There should be a place to keep that. 

# Tools

Recursive call tool: an agent can spawn a subagent of the same scaffold (for now, just make it easy so that there is one model call a time) 

Register modification tool: set one register. This tool must check the validity of the input value (type and length). 

The tools should contain standard tool use (eg. bash and network)

trajectory history: history should be stored elsewhere (eg. in memory) and   
  cannot be modified by the agent. If the agent calls another agent, the log should refer to that trajectory. There should be a tool that reads trajectories. 

The tool response should be stored somewhere, and a reference should be kept in a special register. For example we can put a response ID in the register, and the model can access that response by providing an ID to an extraction tool. The model should also be able to provide a number so that the response extraction starts displaying from the n-th char as provided.

I am thinking of implementing storage as providing the filesystem.

```
[temporary display zone: model's last action along with tool response]

[thinking zone: generated by model]

```

### Code Support

In the first version, let's just make these trajectories and register modification operations available through tool use. The reason is that current agents are trained to use tools. 

We should try if it is better to support them in code, since code is so much more versatile and can support very complex logic. 

A completely code-based version, without further tool use:

```
[system message]
[register zone]
[tool zone]

(all trajectories, registers access available in file system)


```


Model writes code and executes code. Trajectories can be read through code, and registers can be read and written through code (a python library). New models can be called by code.

eg.

```
import infinite
last_tool_response_file = infinite.get_register(0)  # read register

response_summary = infinite.spawn(f"summarize the response file: {last_tool_response_file}")  # call subagent
infinite.set_register(0, response_summary)  # write register

```

The "spawn" function should spawn a new subagent with the user prompt. It is preferred to implement it in this way: the system prompt contains "write your final response to xxxxx" where xxxxx is a file name; the target file name is generated dynamically by the infinite agent system, and is temporary. The function monitors whether the file exists in the end. If the file does not exist, the function spawns a new subagent again. We want the model to provide its response in this way so that they can use programs to generate very long responses. 

## Reading very long content

Models should be able to read very long text. Make it simple for model to scroll text. 

I think it should be good to separate "workspace" with "tool response". Tool response should always be a one-liner. ({"return_value": 0, "response_type": "file", "reference": "example.txt"} etc.) Workspace should be the larger place to read current things. Should be able to use tool to modify workspace. 


## Other thoughts

### PC-style

Register be like:

```
current strategy: None (or a file name)
current action: a short string
```

Design mode: The model writes a strategy code.

The code is then executed. 

For example: assume that the user asks model to handle a request. If the model thinks that the request may be replied by itself, then it replies to that request, else it asks an administrator to chime in (by submitting an escalated event).

Finally it should generate something like this:

```
# strategy code
import infinite

def classify_and_respond(user_request):
    response = infinite.spawn(
        f"The user provides the following request: {user_request}. "
         "If the request is simple and can be replied by yourself, "
         "directly provide a response. Otherwise, escalate to a human."
         "(format)"
	)
	if not response["escalate"]:
	    # call respond API directly
	    # ...
	    infinite.set_register(0, "Response: not escalated. ")
	    response = infinite.spawn(
	        f"The user provides the following request: {user_request}. "
	        f"The system responded with {response['message']}."
	        f"Write a reply to the user about the process result."
	         "(format)"
	    )
	    infinite.reply(response['message'])
	else:
	    # call an escalation API
	    infinite.set_register(0, "Response: escalated. ")
	    # ...
	    
classify_and_respond()

```
